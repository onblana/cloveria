# Cloveria — 게임 기획

## 한 줄 컨셉

클로버의 행운이 깃든 시골 마을에서 직접 농사지은 재료로 요리를 만들어 식당을 경영하는 웹 게임.

## 장르 / 플랫폼

- 농장 시뮬레이션 + 경영 타이쿤
- 웹 브라우저 (짧게 자주 접속하는 세션 구조)
- 톤: 동물의숲 계열(가볍고 꾸미기 중심), 스타듀밸리식 장시간 몰입 아님

## 스토리

클로버 마을에는 오래된 전설이 있다.
이 마을에서 농사를 지으면 클로버의 행운으로 희귀한 작물을 얻을 수 있다는 것.
단, 선택받은 자만이 그 행운을 얻는다.
이제는 아무도 믿지 않는 구닥다리 이야기로, 마을 사람들 사이에 구전으로만 남았다.

어릴 때 마을을 떠났던 `{user}`는 할머니가 남긴 낡은 식당을 물려받아 고향인 클로버 마을로 돌아온다.
돌아온 첫날 밤, 꿈에 클로버의 요정이 나타나는데...

설정상 역할:

- "선택받은 자만이 행운을 얻는다" = 특별 작물 확률의 정당화
- 후속 떡밥: 할머니 역시 선택받은 자였다
- 낡은 식당 = 초기 시설이 허름한 이유를 자연스럽게 설명

## 오프닝 흐름

1. 전설 서술 (텍스트, 스킵 가능)
2. 이름 입력 — "당신의 이름은 무엇인가요?"
3. 캐릭터 커스터마이징 (초기 버전에서는 생략, 추후 삽입)
4. 귀향 장면 — 낡은 식당 도착
5. 첫날 밤, 꿈에서 요정 등장
6. 요정이 토마토 씨앗을 건넴 → 튜토리얼 시작
7. 첫 손님 등장 → 코어 루프 1회 완주

## 코어 루프

```
손님 주문 → 필요한 재료 파악 → 밭에 심기 → 성장 대기 → 수확
→ 레시피 조합 → 요리 제공 → 매출·평판 획득 → 식당 확장/꾸미기 → 새 손님
```

핵심 원칙: **무엇을 심을지는 밭이 아니라 손님이 결정한다.**
농사는 독립 시스템이 아니라 식당 경영의 하위 작업으로 묶인다.

## 차별화 메카닉 — 특별 작물

- 모든 작물에 낮은 확률의 특별 작물 존재 (색·외형이 다름)
- 인접 배치, 날씨, 요일 등 조건으로 특별 작물 확률 변동
- 특별 재료로 만든 요리 = 특별 요리 (가격·손님 반응 상승)
- 희귀한 특별 작물은 판매보다 전시가 이득 → 꾸미기 보상과 연결

## 클로버 요정

- 튜토리얼 안내자
- 특별 작물이 나올 때 반응(반짝임) → UI 피드백 담당 겸임
- 신규 특별 작물 발견 시 도감 기록
- 중반 이후 부재 → 특정 조건에서 재등장하는 진행 축

## 레시피 시스템

- 재료 조합으로 요리 생성
- 같은 레시피라도 사용 재료 등급(일반/특별)에 따라 결과 등급 분화
- 신규 레시피는 평판·손님 요구를 통해 해금

## 캐릭터 커스터마이징

- 헤어, 의상 등 아이템으로 외형 변경
- 초기 버전에서는 미구현. 기본 스프라이트 1종 고정
- 데이터 필드만 선점하여 추후 확장 시 구조 변경 방지

```ts
state.player = { name, appearance: { hair: 0, outfit: 0 } };
```

## 하루 사이클 (1회 3~5분)

- 아침: 밭 확인, 수확, 파종 — 조용함
- 점심: 영업, 주문 처리 — 바쁨
- 저녁: 정산, 메뉴 조정, 식당 꾸미기 — 흐뭇함

## 소셜 (비동기 방식)

- 실시간 멀티플레이 없음. 저장 데이터 스냅샷을 읽기 전용으로 공유
- 다른 유저 식당에 손님으로 방문 → 시식, 별점, 방명록
- 우편함: 선물, 씨앗 교환
- 마을/식당 코드(URL)로 공유

## 기술 스택 (최종 지향점)

- 렌더링: PixiJS (Canvas 레이어 — 맵, 아바타, 작물)
- UI: React (인벤토리, 주문, 상점, 레시피창)
- 상태: Jotai (게임 상태) + TanStack Query (스냅샷 동기화)
- 저장: IndexedDB (idb)
- React DOM으로 타일맵을 그리지 않는다

### 라이브러리 도입 시점

위 스택은 최종 지향점이며 한 번에 설치하지 않는다.
첫 루프는 새 라이브러리 없이 React 기본 기능만으로 구현하고, 실제로 아파질 때 하나씩 도입한다.

| 도입 시점 | 라이브러리 |
| --- | --- |
| 상태 전달이 복잡해질 때 | Jotai |
| 새로고침에 데이터가 날아가는 게 문제될 때 | idb (IndexedDB) |
| 텍스트를 그래픽으로 교체할 때 | PixiJS |
| 스냅샷 공유(소셜)를 붙일 때 | TanStack Query + Supabase |

## 사용 리소스

라이선스와 저작권 고지 의무는 [licenses.md](licenses.md)에 모아 둔다. 여기에는 사용법만 적는다.

### 폰트 — 마루부리 (네이버)

- 제공 굵기는 200 / 300 / 400 / 600 / 700 다섯 가지. **500은 없으므로 강조에는 600을 쓴다**
- `@font-face`를 다섯 굵기 모두 선언하되, 브라우저는 화면에 실제로 쓰인 굵기만 내려받는다

## 결정 사항

### 플랫폼 — 모바일 웹 우선

주 타깃은 모바일 브라우저다. 데스크톱은 같은 화면이 넓게 보이는 정도로만 지원한다.

- 모든 조작은 터치로 가능해야 하며, 키보드 전용 조작(방향키 이동 등)에 의존하지 않는다
- 터치 대상은 최소 44px을 확보한다
- 기기 다크 모드를 따르지 않고 밝은 색조로 고정한다 (게임 화면이 밝은 톤이라 색이 뒤집히면 읽을 수 없음)

### 앱 출시 경로 — 웹 우선, RN 재작성은 배제

React Native로 옮기려면 렌더링 레이어를 통째로 다시 만들어야 한다. PixiJS는 브라우저 canvas/WebGL 위에서만 동작하기 때문이다.
1인 개발 규모에서 감당할 작업이 아니므로 다음 순서를 따른다.

1. 모바일 웹으로 완성 → PWA로 홈 화면 설치 지원
2. 앱스토어 배포가 필요해지면 웹앱을 WebView로 감싸 포장
3. RN 전면 재작성은 네이티브 기능이 반드시 필요할 때만 검토

이 선택지를 열어두기 위해 **게임 규칙은 화면과 분리된 순수 TypeScript로 유지한다** (`src/lib/game/`).
작물 성장, 특별 작물 판정, 가격 계산은 DOM·React에 의존하지 않으므로 렌더링을 무엇으로 바꾸든 그대로 재사용된다.

### 특별 작물 — 용어 통일과 판정 시점

작물의 변이종과 요리의 시그니처 메뉴를 각각 다른 단어로 부르고 있었다.
같은 개념이 코드와 화면에서 세 가지 이름으로 흩어져 읽기 어려워 **`special` 하나로 통일한다** (화면 문구는 '특별 작물', '특별 요리').

- `mutationRate` → `specialRate`, `mutantName` / `signatureName` → `specialName`
- 보유 수량은 `{ normal, special }`
- 요리 쪽은 `signatureMultiplier` → `specialMultiplier`, `canCookSignature` → `canCookSpecial`

판정 시점은 **수확하는 순간이 아니라 다 자라는 순간**이다. 결과는 밭 칸(`Plot.isSpecial`)에 저장한다.

- 수확 버튼을 누를 때 뽑으면 같은 칸을 새로고침할 때마다 결과가 달라져 저장 기록과 어긋난다
- 미리 정해 두면 수확 전에 ✨로 보여줄 수 있어, 유저가 어느 칸이 특별한지 알고 수확 순서를 정할 수 있다
- 판정은 단계가 넘어가는 지점과 저장 기록을 읽는 지점에서만 부른다 (`revealGrownPlots`)

### 시간 축 — 세션 기반

작물 성장은 **접속 중에만 진행되는 게임 내 틱**으로 처리한다. 현실 시간 연동은 채택하지 않는다.

- 하루 사이클이 3~5분이라 현실 시간 단위와 궁합이 맞지 않는다
- 현실 시간 연동 시 개발 중 성장 대기 때문에 테스트 반복이 어렵다
- 추후 현실 시간으로 전환할 여지를 남기기 위해 심은 시점(`plantedTick`)을 기록하는 구조는 유지한다

### 프레임워크 — Next.js

`create-next-app` 기본 템플릿에서 시작했고, 게임 엔진이 아니라 **게임을 감싸는 웹 껍데기**로 유지한다.

실제로 얻는 것:

- 라우팅 — 마을/식당 코드(URL) 공유가 소셜 기능의 전제라 페이지 단위 URL이 필요하다
- `next/font` — 마루부리 다섯 굵기 로컬 폰트 선언과 사전 로드를 이미 여기에 의존한다
- 번들 최적화·PWA 경로 — 모바일 웹 우선 방침에서 초기 로딩이 곧 이탈률이다
- Vercel 배포 — 1인 개발에서 인프라에 쓸 시간이 없다

부담인 것:

- 게임 본체는 canvas 클라이언트 전용이라 SSR·서버 컴포넌트가 거의 쓰이지 않는다. 실제로 `game`·`play` 페이지는 모두 `'use client'`다
- Supabase는 클라이언트와 키만 준비된 상태이고 호출하는 코드가 아직 없다. 저장은 IndexedDB가 전담하므로 서버 실행이 필요한 지점 자체가 없다
- Vite 대비 dev 서버·빌드가 무겁다

정리하면 남는 이득은 **라우팅·폰트·배포 세 가지**다. 이것으로 충분하다고 보고 유지하되, 서버 실행이 필요해지는 시점(스냅샷 공유 링크의 메타태그 생성, Supabase 키를 숨겨야 하는 요청)이 오면 그때 서버 라우트를 도입한다. 그 전까지 Next.js 고유 기능에 게임 로직을 묶지 않는다.

## 첫 구현 목표

그래픽 없이 텍스트·버튼만으로 코어 루프 한 바퀴를 완주한다.

```
이름 입력 → 손님이 토마토 파스타 주문 → 토마토 심기 → 성장
→ 수확 → 요리 제공 → 보상 획득 → 씨앗 재구매 → 다음 손님
```

작물 1종, 레시피 1종으로 시작하되 특별 작물 판정은 포함한다.
특별 작물은 이 게임의 차별화 지점이라 루프의 재미를 초기에 검증할 필요가 있다.
